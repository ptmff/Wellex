# Отчёт о тестировании бэкенда Wellex

Ветка `tests/full-suite`. Все цифры ниже взяты из реальных прогонов; логи и JSON-отчёты Jest лежат в
[`run-logs/`](run-logs/). Прогоны выполнялись на изолированном тестовом стенде (не на проде wellex.fun):
отдельная тестовая БД `prediction_market_test` и Redis DB 15.

## 1. Стенд

| Компонент | Версия (локальный прогон) | В GitHub Actions |
|---|---|---|
| Node.js | 24.22.1 (основные прогоны), 20.20.2 (контрольный прогон `04`) | 20 |
| PostgreSQL | 16.16 | `postgres:16-alpine` |
| Redis | 8.0.2 (в Debian 13 нет пакета Redis 7) | `redis:7-alpine` |
| Jest / ts-jest / supertest / ws | 29.7.0 / 29.4.6 / 7.3.2 / 8.19.0 | те же (из `package-lock.json`) |

Схема БД создаётся настоящей миграцией `src/database/migrations/001_initial_schema.ts` (global setup пересоздаёт
схему `public` тестовой БД). Перед каждым тестом все таблицы очищаются (`TRUNCATE ... CASCADE`), тестовый Redis
очищается через `FLUSHDB`. Защита: набор не запустится, если в имени БД нет `test`.

## 2. Что изменено

* Удалены 4 старых набора (97 тестов). Они не импортировали `src`, а копировали логику внутрь тестов, поэтому
  покрытие было 0 %. Среди них был тест LMSR-движка, который удалён из кода (с марта 2026 работает order book).
  Исходный прогон старых тестов: 4 набора, 97 passed, покрытие 0 % (0/3099 statements). Лог:
  [`run-logs/00-baseline-main-original-tests.log`](run-logs/00-baseline-main-original-tests.log).
* `jest.config.json`: исправлена опечатка `coverageThresholds` → `coverageThreshold` (раньше порог не
  проверялся вообще). Добавлены два проекта: `unit` (без БД) и `integration` (Postgres + Redis), последовательный
  запуск (`maxWorkers: 1`), отчёты покрытия `text`, `lcov`, `html`, `json-summary`.
* Порог покрытия выставлен по фактическим цифрам с небольшим запасом: statements 70, branches 40, functions 70,
  lines 75 (раньше в конфиге было 60/60/60/60, но порог не работал из-за опечатки). Ветвления пока покрыты на 44,66 %,
  поэтому общий порог 60 % по branches не выполняется. Поднять его можно позже, когда будут покрыты ingest, YooKassa и market-maker.
* `src/app.ts`: сборка Express-приложения вынесена из `src/main.ts` в функцию `createApp()` без изменения
  поведения. Это нужно, чтобы supertest поднимал настоящее приложение. `main.ts` по-прежнему подключается к БД,
  выполняет миграции и сиды, запускает фоновые задачи, `listen` и graceful shutdown.
* Добавлены devDependencies `supertest` и `@types/supertest`, скрипты `test:unit`, `test:integration`,
  `test:cov`, `test:ci`, `typecheck:test`, а также `tsconfig.test.json`.
* `.github/workflows/backend-tests.yml`: Node 20, сервисы `postgres:16-alpine` и `redis:7-alpine`, проверка типов,
  тесты с покрытием, артефакт `backend-coverage`.

10 падений в прогоне 01 вызваны реальными дефектами кода (раздел 6). Тесты под них не подгонялись. В финальной
версии они помечены `it.failing('[BUG-xx] …')`: такой тест проходит, пока баг есть, и падает, когда баг
исправят. Тогда его нужно вернуть в обычный `it(...)`.
В первой серии повторов (`03-stability-3-runs.log`) один раз упал тест ротации refresh-токена. Причина в BUG-06:
код с вероятностью 5 % сам удаляет отозванные токены. В этом тесте `Math.random` зафиксирован, а сам дефект
проверяется отдельным тестом. После этого 10 повторов подряд прошли без падений.

Состав (прогон 02): unit — 3 набора / 15 тестов; integration (сервисы на реальных Postgres+Redis) — 5 / 50;
API (supertest + WebSocket) — 4 / 37.

## 6. Найденные дефекты (не исправлены, зафиксированы тестами)

| ID | Где | Суть | Как проявляется |
|---|---|---|---|
| BUG-01 | `orderbook.service.ts:211, 2010, 2071` и `:2086` | Кэш снимка стакана пишется по ключу `book:<id>:<depth>`, а удаляется по `book:<id>`. Инвалидация не срабатывает | До 2 с API отдаёт старый стакан (подтверждено тестом). По коду в WebSocket тоже уходит старый снимок: рассылка в `setImmediate` читает тот же кэш |
| BUG-02 | `orderbook.service.ts:526` | При минте пары, если тейкер покупает NO: `yesPrice = 1 − priceB`, хотя `priceB` уже цена YES | После YES@0,60 + NO@0,45 цена YES = 0,40 вместо 0,55–0,60 |
| BUG-03 | `executeMarketTrade`, циклы `:1148` и `:1366` | В рыночной сделке нет проверки на самосделку, хотя в лимитном сведении она есть (`:288`, `:322`) | Пользователь покупает у себя, платит 2×0,5 % комиссии, растут объём и `trade_count` |
| BUG-04 | `orderbook.service.ts:990, 1161` | Количество считается как `budget / (price·1,005)`, затем стоимость сравнивается с бюджетом. Из-за округления Decimal (20 знаков) стоимость превышает бюджет на 1e-19, и цикл прерывается | Покупка на 2 WX при цене 0,50 отклоняется с «No enough liquidity», хотя ликвидность есть (подтверждено тестом). | BUG-05 | `portfolio.service.ts:36` | `pnl.realized` = все денежные потоки по сделкам, то есть затраты на открытые позиции. Unrealized тоже считается от средней цены, и стоимость покупки учитывается как убыток дважды | После покупки на 5,5 WX total PnL = −5,5275 вместо −0,0275 |

| BUG-07 | `admin.router.ts:84` | Запрос `count(*)` клонируется вместе с `ORDER BY created_at` | `GET /admin/users` → 500 (`column "users.created_at" must appear in the GROUP BY clause`) |
| BUG-08 | `common/errors.ts` (обработчик PG-ошибок) | Код `22P02` (некорректный uuid) не обрабатывается | `GET /orders/abc`, `GET /markets/abc` → 500 вместо 400/404. Вне production в ответе виден SQL |
| BUG-09 | `ws.service.ts:202` и `:283` | `broadcastToMarket` отправляет событие напрямую и публикует его в Redis. Тот же инстанс подписан на `market:*` | Каждое событие рынка приходит подписчику дважды |
| BUG-10 | `src/app.ts:96, 113, 127` (раньше `main.ts`) | `keyGenerator` использует `req.user?.id`, но limiter стоит до `authenticate()`, поэтому `req.user` всегда пуст | Торговый, экономический и общий лимиты считаются по IP, а не по пользователю. Пользователи за одним NAT мешают друг другу |

Наблюдения без отдельного теста: кэш рынка (30 с) и портфеля (10 с) не сбрасывается после сделок, это компромисс
TTL. Кэш пользователя в `authenticate()` живёт 60 с, но при бане через admin API он сбрасывается (T-08). После
окончания блокировки счётчик `failed_login_attempts` не обнуляется, поэтому одна следующая ошибка снова блокирует аккаунт.

## 7. Как воспроизвести

```bash
# 1. Postgres 16 и Redis 7 — любой способ, например из docker-compose проекта:
cd backend
docker compose up -d postgres redis          # Postgres на localhost:5433, Redis на 6379
docker compose exec postgres createdb -U postgres prediction_market_test
#    (без Docker: локальные postgresql-16 + redis-server с теми же портами)

# 2. Тесты (секреты не нужны — тестовые значения задаются в test/setup/env.ts)
npm ci
npm run typecheck:test
npx jest --coverage --ci            # всё: unit + integration + API
npm run test:unit                   # только unit (без БД)
npm run test:integration            # только Postgres/Redis
```

Переменные `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `REDIS_HOST`, `REDIS_PORT`, `REDIS_DB`
можно переопределить. Имя БД обязательно должно содержать `test`. В CI это делает
`.github/workflows/backend-tests.yml`.
